# ADR 0030: Expert decisions are made under a deadline and written down

- Status: Accepted, 2026-11-15, by the agent under the design authority ADR 0021 records.
- Scope: how the live game asks an Expert villager for a play, and how a save replays it. It settles what ADR 0009 and ADR 0011 left to "when the search is wired into the game".

## The problem

`RunLoop` asks every villager for its play through `Bot.decide_play` with an unlimited budget. Three tiers answer from rules and that is cheap. The Expert tier searches: up to 48 deals of the unseen cards, up to three candidates played out in each. `ExpertRunner`, which spreads that search over the worker pool and stops starting new samples at a deadline, is used by a measuring tool and by tests, and never by the game.

The balance harness (P4.16) first measured a searched Expert decision on the game's own path at about 2.3 seconds on average and 4 at worst, inside runs that shared the processor with seven others. Measured alone on one thread it is 0.9 seconds on average and 3.8 at worst (`docs/perf.md`), on the thread that handles the player's command. An unlimited search on that thread is far outside P2.9's budget of a p99 under 400 ms on a worker with a deadline. Two families are Expert: Ma, who joins the village after three finished runs, and Tang, after five. Nobody else can reach the tier: rising families stop at Hard.

A deadline cannot simply be dropped in, because of how saves work. A run save is a checkpoint and the player's commands since; loading replays those commands, and the villagers decide again as the replay goes. A decision that depends on a clock is not repeatable. The replay could then differ from what the player saw.

## Decision

1. **A config says whether it searches.** `BotConfig` answers it (Expert today), so a later searching tier is covered in one place.
2. **The loop asks a searcher.** `RunLoop` gets an optional searcher, a callable with `Bot.decide_play`'s inputs that returns a play. It is asked only for a searching seat. With none, the loop calls `Bot.decide_play` with the unlimited budget as today. The tournament plays through `SelfPlay` and the harness through a loop with no searcher, so both stay repeatable.
3. **The game supplies `ExpertRunner`** with a deadline kept in data (300 ms, the figure ADR 0011 measured with). At the deadline the runner starts no more samples and decides on those finished; a sample already running completes first, so a decision can run a little past the deadline. ADR 0011 recorded a p99 of 357 to 376 ms that way.
4. **Every decision by a searching seat is written down**, whether the search overturned the policy's play or not, since either can depend on the clock. The run record gains a list beside the player's commands: each such decision since the checkpoint, in order, as the seat and the card IDs played, or a pass. It is cleared with the commands at each checkpoint.
5. **Replay reads the list and nothing else.** The list is handed to the loop before the checkpoint is resumed, because villagers can act before the first replayed command. During replay a searching seat takes its play from the list. The load fails, as it does for a command that no longer applies, if the next entry is for another seat, is not a legal play there, if the list runs out while a command is still to be replayed, or if entries are left over when it ends. A list that runs out inside the last command is not a fault: the game also saves at each state move, which can fall inside a command before the villagers have played, and a game that stopped there never showed those plays. They are decided then, live. After the replay, play goes on with the searcher.
6. **Older saves.** The run save moves up a schema. A migrated save is marked as holding no written decisions, and replays with the unlimited search, as it was made.

## Consequences

- Loading a save in the middle of a Quota no longer repeats every search made so far.
- The game still waits for the Expert on the thread that handles the player's command. One command can be followed by two Expert decisions before the player's next turn, so the pause after a play can reach about two deadlines, and P2.9's budget is a p99, not a ceiling. Whether that is felt is for the playtest. Moving the wait off that thread means the loop must be able to stand still for a villager as it does for the player; that is a new checklist item (P5), not part of this change.
- The live figure has to be measured once the game uses the runner, and recorded in `docs/perf.md`, as ADR 0011 asked.
- The harness keeps the unlimited, repeatable search. Because that is slow, it may lower the number of deals an Expert samples (`--expert-samples`, never below the 12 a search needs before it may overturn the policy), and says so in its report. How much weaker that makes Expert villagers has not been measured.

## Amendment, 2026-11-17: the loop stands still for a search (P5.0)

The second consequence above is now done. The game no longer waits for an Expert villager on the thread that handles the player's command.

- **Core stands still.** `RunLoop.Awaiting` has a value for a villager whose play is being searched, `VILLAGER_SEARCH`. When `SearchedDecisions.answered_outside` is set and a searching seat is to play live with moves to choose from, the loop sets it and returns, as it does for the player. `RunLoop.search_request()` gives the search what it reads, as a `SearchRequest`: the seat, and copies of its view, its legal moves, its rules and its config, with any weights handed in. `RunLoop.villager_play(play)` takes the play, checks it as any bot's play is checked, writes it with the decisions and plays on. It is not a player command and is refused in any other state. Player commands and the books command are refused while the loop stands still for a villager. The flag is off by default, so every tool and test plays as before, and core gets no thread or clock.
- **The game searches on the pool.** `ExpertRunner.start` begins a decision and returns at once, and `is_finished` takes it on each time it is polled. The deadline rule is unchanged, and each worker now reads the clock itself before it starts a sample. `RunController` sets the flag when it searches live. In the tree, `VillagerSearches` runs the search and `_process` hands the play in, then the controller flushes the log, saves, seals the second book again and emits `awaiting_changed`. Outside the tree the controller searches at once on its own thread, as before, so callers that never run frames are unchanged. A search for a loop the controller let go of, or that no longer waits on that request, finishes and is thrown away. Leaving the tree waits for every running search, so no worker outlives the runner it calls.
- **One thread is left for the table.** The samples are spread over every processor thread but one. With all of them searching, a frame was once measured at 44 ms against the item's 50 ms; with one left free the longest frame while a villager thought was 7 to 27 ms over 1,300 frames, on the development PC. `decide` keeps to the same count, so `tools/expert_deadline.gd` measures what the game plays with. An Expert finishes a few samples fewer inside its deadline for it.
- **A running sample has a grace, then it is abandoned.** Rule 3 let a sample already running at the deadline finish, however long it took. The full measurement (`docs/perf.md`) put the p99 of a decision at 401 ms, and 426 ms with a wild rank, against P2.9's 400 ms, and a slower machine would be further over. A sample now has `expert_grace_usec` (60 ms, in the weights) past the deadline. After that it stops between two steps of its rollout and counts as not finished. Core still has no clock: the runner hands each sample a `BotBudget`, as `Bot.decide_play` already takes one. A decision is then over about 360 ms after it began on any machine.
- **Saves.** A save written while a villager thinks ends before its play. Rule 5 already lets the list of written decisions run out inside the last command, so the save loads, and with the flag set (`RunRecord.resume`'s `outside`) the loop comes back standing still for that villager and the search starts again. No schema change.
- **The second book.** A villager's play can end a round and bank Grain, so the book is sealed again after the play is applied (ADR 0022). While a villager thinks the detectors correct nothing, since the books command waits on the player. A figure changed from outside during the search is therefore sealed in with the play, and the book does not see it. The window is the length of one search.
